## MVP
клопслоп мой любимый

### Регистрация и авторизация
Username + пароль. Регистрация нужна для создания комнаты; для участия в партии по приглашению она не обязательна (см. ниже).
jwt токен в куках лежит, пароль лежит в хешированном виде

### Комнаты и приглашения
Матчмейкинга нет. Авторизованный пользователь создаёт комнату и получает пригласительную ссылку — URL с уникальным токеном комнаты. Ссылку он отправляет собеседнику любым внешним способом (Telegram и т.п.), доставку самой ссылки приложение не обеспечивает.

Переход по ссылке:
- если человек авторизован — присоединяется под своим аккаунтом;
- если не авторизован — присоединяется как анонимный гость, с временным отображаемым именем, без создания аккаунта.

Как только в комнате оказываются два разных участника — партия начинается. Стороны соперников рандомятся, возможности выбора стороны на стадии MVP не буде
Комната и партия используют один и тот же URL на всём протяжении — от ожидания второго игрока до конца партии.

### Шахматная логика
Полная реализация правил: ходы всех фигур, рокировка, взятие на проходе, превращение пешки, шах/мат/пат, ничья.

### Живой геймплей
Ходы и обновление состояния доски — через WebSocket, без перезагрузки страницы и смены URL, и во время ожидания второго игрока, и во время самой партии.

## Технологии

### Шахматный движок
Python, без внешних зависимостей внутри самого движка. FEN — сериализация позиции. pytest — тестирование.

### Backend
FastAPI, WebSocket, чистый SQL без ORM. Гостевая идентичность — токен в cookie, не персистентная, существует только в памяти на время жизни комнаты. Комнаты и активные партии — в памяти процесса, не в БД.

### Frontend
Jinja2 + htmx — создание комнаты, страницы входа/регистрации. TypeScript — WebSocket-клиент и отрисовка доски на странице комнаты, в обоих состояниях: ожидание и партия. Клиент не содержит шахматную логику, только отображение состояния и отправку намерений. Сборка — esbuild/tsc. CSS — Pico.css/simple.css. Короче фронтенд пусть нейронки пишут на тайпскрипте. Я ебал это в рот все.

### REST API

| Метод | Путь | Назначение |
|---|---|---|
| POST | /api/auth/register | Регистрация (username, password) |
| POST | /api/auth/login | Вход, сессионная cookie |
| POST | /api/auth/logout | Выход |
| POST | /api/rooms | Создать комнату (только авторизованный), вернуть room_id |

### Страницы

GET /room/{room_id} — единственная игровая страница. Определяет, кто зашёл (авторизованный пользователь или гость), при необходимости выдаёт гостевой токен, дальше всё состояние — через WebSocket на этой же странице.

### Протокол WebSocket

Подключение: /ws/rooms/{room_id}

| Направление | Тип | Содержимое |
|---|---|---|
| Клиент → сервер | move | from, to, promotion? |
| Сервер → клиент | state | fen, turn, status, result? |
| Сервер → клиент | move_rejected | reason |
| Сервер → клиент | room_full | — (после этого соединение закрывается) |

status принимает значения: waiting_for_opponent, ongoing, checkmate, stalemate, draw. result заполняется только в терминальном статусе.

## Открытые вопросы

1. Переподключение к своей же комнате (обновление страницы) не должно приниматься за нового второго игрока. Решение: identity (user_id для авторизованных, guest_token из cookie для гостей) проверяется против уже занятых слотов комнаты перед тем, как занять свободный.
2. Токен комнаты в URL — единственный контроль доступа к партии, поэтому должен быть криптографически случайным (например, secrets.token_urlsafe), не последовательным числом.
3. Комнаты, к которым никто не присоединился, сейчас ничем не вычищаются из памяти. Для двух человек не критично; при более широкой эксплуатации стоит добавить периодическую очистку неиспользуемых комнат.
4. Если рейтинг ELO вернётся из бэклога — партии с участием анонимного гостя рейтинговыми быть не смогут: у гостя нет постоянной идентичности между партиями. Учесть при реализации соответствующего пункта бэклога.
